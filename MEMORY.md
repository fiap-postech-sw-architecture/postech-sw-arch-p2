## Gotchas

- 2026-06-12 - [in-flight from feat/i11-otel-minimo] `_log.info(...)` de src/ NAO aparece no stdout do container: structlog usa stdlib LoggerFactory e o root logger fica no default WARNING (nenhum basicConfig/handler no boot) — so warning+ sai (via lastResort do stdlib). Nao valide feature por log de info; confirme por efeito observavel (ex.: API do Jaeger) ou logue warning
- 2026-06-12 - [in-flight from feat/i6-email-status] `structlog.testing.capture_logs` NAO intercepta logger module-level (`_log = structlog.get_logger(__name__)`) que ja foi usado depois de um boot do app: `configurar_logging` usa `cache_logger_on_first_use=True`, entao quando a suite de integracao (roda antes de `unitarios/` na ordem alfabetica) exercita o caminho que loga, o proxy cacheia os processors de PRODUCAO e o capture dos testes unitarios ve lista vazia — falha so na suite completa, passa em isolamento. Correcao padrao: fixture autouse no arquivo de teste monkeypatchando o `_log` do modulo por um proxy novo (`structlog.get_logger("test_x")`) — ver `test_notificacoes.py`/`test_dispatcher.py`
- 2026-05-03 - [in-flight from PR #139] `make ghcr-prune` no Git Bash do Windows precisa de DOIS workarounds simultaneos: (a) `MSYS_NO_PATHCONV=1` no `bash -c` envolvente -- senao MSYS reescreve `/user`, `/users/...` em arg do `gh.exe` (binario Windows nativo) pra `C:/Program Files/Git/user`, e a Github API rejeita; e (b) `| tr -d "\r"` entre `jq -r ...` e `while read -r id` -- senao o id captura `\r` final (gh.exe e jq.exe emitem CRLF) e a URL DELETE seguinte vira `.../versions/838326537%0D` que Go net/url rejeita ("invalid control character in URL"). Aplicaveis a qualquer chamada de binario Windows nativo no Makefile que receba paths Unix-like ou cujo stdout vire input de `read`. Tambem: o pipeline `update-ghcr` agora patcha `db-image/docker-compose.yml` ANTES do prune e trata prune como best-effort (`|| echo "..."`), garantindo consistencia compose<->GHCR mesmo se o prune falhar -- se o patch viesse depois e o prune morresse com `set -e`, a NEW_KEY ficava perdida no scope bash e nao havia recovery automatico
- 2026-05-03 - [in-flight from PR #139] `docker compose up` retorna assim que o entrypoint do container dispara, MUITO antes do uvicorn realmente atender. Resultado: porta 8000 ja aberta (Docker proxy escutando) mas browser leva `ERR_EMPTY_RESPONSE` por dezenas de segundos -- piora drasticamente sob emulacao QEMU (~40s observado em maquina amd64) quando imagens publicadas em arm64 rodam emuladas. Solucao em `db-image/docker-compose.yml`: healthcheck no `app` probando `/api/v1/saude` via Python+urllib (NAO `curl`/`wget` -- podem nao estar na imagem slim do FastAPI), `start_period: 30s` pra cobrir QEMU sem marcar unhealthy, `ui.depends_on.app.condition: service_healthy` (era `service_started`), e o QUICKSTART agora documenta `docker compose up -d --wait` pra terminal segurar ate todos os healthchecks passarem. Sem o healthcheck, `--wait` nao tem o que esperar e o ganho some
- 2026-05-01 - [in-flight from PR fix/all] PostgreSQL serializa DELETE em uma tabela referenciada via FK e INSERT na tabela referenciadora atraves do conflito ``FOR UPDATE`` × ``FOR KEY SHARE``: a validacao de FK em INSERT pega ``FOR KEY SHARE`` na linha referenciada, que conflita com o ``FOR UPDATE`` adquirido pelo lado do DELETE. Em `RemoverVeiculo`, `ClienteRepository.bloquear_veiculo_para_remocao(veiculo_id)` (`select(...).with_for_update()` em `veiculos.id`) fecha a janela de corrida com criacao concorrente de OS — sem precisar mexer no caminho de criacao. O lock e silent no-op se a linha nao existir; o caller ja validou a presenca no agregado
- 2026-04-29 - Em macOS com Colima, testcontainers (suite de integracao) precisa de duas variaveis pra achar o socket: `DOCKER_HOST=unix:///Users/<user>/.colima/default/docker.sock` (o cliente docker) e `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` (o path que o testcontainers passa pra dentro do ryuk container). Sem o override do socket, ryuk tenta montar o path literal do host (`.colima/default/...`) que nao existe dentro da VM e o teste falha com "operation not supported"
- 2026-04-29 - SQLAlchemy ORM imperative mapping: o evento `load` so dispara no PRIMEIRO carregamento de uma instancia. Apos `session.expire(obj)` + re-fetch na mesma sessao, o evento que dispara e `refresh` (assinatura diferente: `target, context, attrs`). Listeners que reidratam VOs precisam estar registrados em ambos — `cliente_veiculo/infraestrutura/mapping.py` ilustra o padrao com `_reidratar_documento` chamado por `_reconstruir_documento_on_load` e `_reconstruir_documento_on_refresh`. Sem o listener de refresh, `repository.anonimizar_dados` + `session.expire_all()` + `obter_por_id` retorna o documento ANTIGO em memoria
- 2026-04-26 - On Git Bash (MSYS2) absolute Unix-style paths (`/tmp/foo`) passed as args to native Windows binaries (e.g. `docker.exe`) are auto-translated to Windows paths (`C:/Users/.../Temp/foo`); the Makefile prefixes `MSYS_NO_PATHCONV=1` on `docker compose cp/exec` lines that pass `/tmp/...` to keep the path literal inside the container.
