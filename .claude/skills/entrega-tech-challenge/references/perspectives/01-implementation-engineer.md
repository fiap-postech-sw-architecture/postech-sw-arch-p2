# Perspective 1: Implementation Engineer

## Focus

Correctness, edge cases, error handling, code completeness.

## Prompt prefix

You are a senior implementation engineer reviewing this for correctness and completeness. Check for: missing edge cases, unhandled errors, incomplete implementations, off-by-one errors, null/None handling, resource leaks.

## Checklist (mandatory, every item must be verified)

1. Protocol and context-manager methods use exact stdlib types: `type[BaseException] | None` for `exc_type`, `BaseException | None` for `exc_value`, `TracebackType | None` for `exc_tb`. Reject widened types (`object`, `Any`) where a precise type exists.
2. `__enter__` returns the concrete class or `Self`, never `object`. `__exit__` returns `bool | None` if it suppresses exceptions, `None` otherwise.
3. All error paths return or raise; no silent `except: pass`, `except Exception: pass`, or naked `return` after a raise.
4. Inputs validated before use: None, empty string, zero, negative, max length boundaries. Every assumption about input shape has a corresponding guard. **Audit every public mutator, not just `__post_init__`/`__init__`**: if a field is `Optional` by type but required by contract, the construction-time guard AND every setter/updater/refresh method must raise the same `ValueError`. Review PR #59 missed the `ServicoOferecido.atualizar(preco=None)` gap because the reviewer stopped after checking construction.
5. Resource cleanup is guaranteed (context managers, `try/finally` for files, sockets, DB sessions). **Never call `next()` on a generator-based dependency (e.g., `next(obter_session())`) outside of FastAPI's `Depends` lifecycle** — the generator suspends at `yield` and its `finally` block (which calls `session.close()`) never executes, leaking the connection. If a function needs a DB session outside a route handler, it must either (a) accept the session as a `Depends`-injected parameter, or (b) use a full `contextlib.contextmanager` wrapper that guarantees cleanup. PR #64 Copilot catch: `obter_usuario_atual` used `next(obter_session())` and leaked a connection on every authenticated request.
6. No `# type: ignore` without an inline comment justifying it, and no `# type: ignore` without a specific error code.
7. Concrete implementations of a Protocol implement EVERY method the Protocol declares (otherwise mypy strict will reject them — this is a common hidden bug source).
8. **Protocol-vs-Union change audit**: when a dependency's type changes from a `Union` (e.g., `CPF | CNPJ`) to a `Protocol` (e.g., `Documento`), re-audit every consumer **in every layer** (application, infrastructure, interfaces). Binary `isinstance(x, Concrete) else "other"` helpers silently mislabel future structural implementations. Use an explicit `isinstance` chain with a `raise` on the unknown case. SQL mapping event listeners and repository decomposition code are especially easy to miss.
9. **`@dataclass(slots=True)` has NO `__dict__`**: never use `obj.__dict__` on a slotted dataclass — it raises `AttributeError` at runtime. Use explicit field access (`Model(id=dto.id, name=dto.name)`) or `dataclasses.asdict(obj)` to spread into a Pydantic model or another dict-based target. Regular non-slotted dataclasses have `__dict__`, but any DTO with `slots=True` does not. **Do not confuse this with Python 3.12's `__dict__` support on classes — that applies to regular classes, NOT to `slots=True` dataclasses.** Production bugs of this shape are common because mocks like `SimpleNamespace` and `MagicMock` happily return a `__dict__`, hiding the failure in tests. PR #64 Copilot catch: `UsuarioResponse(**result.__dict__)` where `result` was a `UsuarioDTO(frozen=True, slots=True)`. All unit tests passed because the mock returned a `SimpleNamespace` with `__dict__`.
10. **Paginated SQL queries require explicit `order_by`**: `select(...).offset(n).limit(k)` without ordering is implementation-defined. SQL engines may return different rows in different orders across calls, causing clients to see duplicates or skipped items. Every paginated query must have a deterministic `order_by` before the offset/limit.
11. **SQLAlchemy `load` listeners must re-establish every `__post_init__` invariant the ORM skips.** SQLAlchemy imperative mapping does NOT call `__post_init__` when rehydrating an entity, so any state that `__post_init__` normally sets must be re-armed in the `@event.listens_for(Cls, "load")` handler. Concretely: `Entity._id_atribuido = True` (otherwise `Entity.__setattr__` will not lock `id` on loaded instances), any VO reconstructed from decomposed columns, and any cached/derived fields. Trace `Entity.__post_init__` + the subclass's `__post_init__` line by line and confirm each assignment has an equivalent `object.__setattr__(target, ..., ...)` in the load listener. PR #60 Copilot catch: all three imperative mappings (estoque, catalogo_servicos, cliente_veiculo) were missing the `_id_atribuido` re-arm and silently allowed mutating `id` on loaded entities.
12. **Three-phase ordering when a method combines state-machine validation with business computation.** Any aggregate method that (a) validates a state transition AND (b) performs non-trivial work (computing a VO snapshot, calling a port, mutating collections) AND (c) mutates state must follow this exact order: **(1) validate transition without mutation → (2) validate business invariants (cheap guards) → (3) perform computation → (4) apply the transition → (5) commit side effects → (6) emit events.** Collapsing to two phases produces one of two bugs: (i) compute-then-mutate leaves the aggregate inconsistent if computation raises; (ii) mutate-then-compute changes error precedence so calculation errors or guard errors take priority over the more fundamental `TransicaoStatusInvalidaException`. The fix is to split the state-transition helper into `_validar_transicao(novo)` (validates, no mutation) and `_aplicar_transicao(novo)` (mutates, no validation), plus keep `_transicionar(novo)` as a convenience for simple methods that have no intermediate work. Review each complex transition method and confirm it calls the validator first, then does work, then calls the applier. PR #61 Copilot catch: `gerar_orcamento` and `gerar_orcamento_complementar` had this bug after PR 09's reviewer fixed only the compute-then-mutate half.

13. **ORM event listener data-flow tracing for repository write methods.** For every repository method that writes data (`salvar`, `anonimizar_dados`, `atualizar`, etc.), mentally execute the full SQLAlchemy event pipeline: method body → `session.flush()` → `before_insert`/`before_update` listeners → actual SQL. Verify the persisted values match the method's intent. ORM listeners can SILENTLY OVERWRITE values written in the repository method. Example (PR #65 Copilot catch): `anonimizar_dados` wrote `"ANONIMIZADO"` to `_documento_numero` and `_documento_hash`, but the `before_update` listener recalculated both from `_documento` (which still held the original PII). The fix was to bypass the ORM entirely with a raw SQL `UPDATE`. This class of bug is invisible in unit tests that mock the session.
14. **`else` fallback in ORM listeners and decomposition functions is a data corruption risk.** Binary `if X else Y` patterns in `before_insert`/`before_update`/`load` listeners silently produce wrong values when a third type is added. Always use explicit `if/elif/else` with a `raise` on the unknown case. PR #65 Copilot catches: `_decompor_documento` wrote `"cnpj"` for any non-CPF document; `_reconstruir_documento` instantiated `CNPJ` for any non-`"cpf"` tipo.
15. **DTOs carrying PII must use `field(repr=False)` on sensitive fields.** Fields like `nome`, `documento`, `contato`, `email` will appear in tracebacks, log messages, and debugger output via `__repr__`. Mark them `field(repr=False)` in the dataclass definition. This applies to BOTH input DTOs (e.g., `CriarClienteDTO`) and output DTOs (e.g., `ClienteDTO`, `DadosPessoaisDTO`). PR #65 Copilot catch: all cliente DTOs exposed PII in repr.
